# Designing Idempotent Boundaries

Assume every handler runs more than once for the same event. That is not a
pessimistic edge case, it is the delivery guarantee almost every real system
offers, and code that assumes otherwise fails in ways that are hard to attribute
because the second delivery looks exactly like a legitimate first one.

## At-least-once is the default, including yours

Exactly-once delivery across a network is not available. What providers, queues,
and clients actually offer is at-least-once, and the duplicate arrives for
mundane reasons:

- The provider did not receive your acknowledgement and retried, though you had
  already committed.
- A client timed out and resubmitted while the first request was still running.
- A user double-clicked, or a mobile client retried on a network change.
- A deployment replayed an unacknowledged batch.
- An operator re-ran a job to fix something unrelated.

Note that the first case cannot be engineered away from your side. The commit and
the acknowledgement cannot be made atomic across a network, so a window always
exists where you have done the work and the sender does not know.

This applies equally to retries **you** add. Wrapping a call in a retry converts
a caller into a duplicate producer; if the callee is not idempotent, the retry is
a new bug rather than resilience. A retry around a non-idempotent side effect is
strictly worse than no retry, because it fires exactly when the system is already
struggling.

## The key must come from the sender

Deduplication requires a stable identifier for the logical event, and it has to
be assigned by whoever is retrying — not generated by the receiver.

A key the receiver mints is a fresh value on every delivery and deduplicates
nothing. A key derived from the payload's contents is better but fails for
legitimately identical events: two purchases of the same item, at the same price,
in the same second, are distinct events with identical bodies.

In order of preference:

1. **An identifier the sender supplies and repeats on retry.** Most providers
   offer one; if you are the sender, generate it at the point where the intent
   forms and carry it through every attempt.
2. **A natural key from the domain** that is genuinely unique per event — an
   order number, a transfer reference.
3. **A content hash plus a sender-supplied sequence number**, when nothing else
   exists.

Record the key in the same transaction as the effect. A dedupe table written
separately from the work it guards has a window where the effect commits and the
record does not, which reintroduces exactly the duplicate you were preventing.
A unique constraint on the key turns the second attempt into a constraint
violation you can catch and treat as success.

## Idempotent is not the same as ignoring duplicates

Returning early on a duplicate is correct only when the first attempt *finished*.
If it failed midway, the second delivery is the retry that should complete the
work, and swallowing it strands the operation permanently.

Record the outcome alongside the key, not just the key:

- **Completed** — return the original result. The caller must see the same
  response the first attempt produced, not a generic acknowledgement, because it
  may be waiting on a value.
- **In flight** — the first attempt still holds the claim. Refuse or wait; do not
  start a second.
- **Failed terminally** — decide explicitly whether the retry may proceed.

This is why "check if a row exists, skip if it does" is insufficient: the row's
existence does not tell you whether the work behind it succeeded.

## Order is not guaranteed either

Deliveries can arrive out of order, so a handler that applies a state change must
tolerate an older event arriving after a newer one. Guard with a monotonic value
carried by the event — a version, a sequence number, a provider timestamp — and
ignore transitions that move backwards.

Without this, a stale retry of "pending" can overwrite a committed "settled" and
the record silently reverts. The system then reports a state that never occurred
after the one that did.

## Confirming a destructive bulk action

An operator confirming "refund 400 orders" is agreeing to a specific set of
effects that were computed at some earlier moment. Between the preview and the
confirmation, the set can change — orders settle, refunds land, someone else acts.

Make the confirmation reference the exact set it was shown:

1. Compute the effects and show them.
2. Hash the computed set, and return the hash with the preview.
3. Require the hash on confirmation. Recompute, compare, and refuse if it differs.

A refusal here is not an obstacle: it is the system reporting that what the
operator approved is no longer what would happen. Re-preview and let them decide
again. Without this, a confirmation is an instruction to act on whatever the set
happens to be *now*, which is not what anyone believes they are approving.

The same pattern applies to any confirm-after-preview flow where the underlying
data is live. `designing-agent-friendly-clis` owns the command-line surface of
this — the dry-run flag, the confirmation default, and what a repeated invocation
should report. This skill owns what has to be true underneath for that repeat to
be safe.

## Review checklist

- What happens if this handler runs twice with the same input? Trace it, do not
  assume.
- Where does the deduplication key come from, and does the sender repeat it?
- Is the key recorded in the same transaction as the effect it guards?
- Does the record store the outcome, so a retry after a partial failure can
  finish rather than being silently skipped?
- Does a duplicate return the original response, or a different one?
- Can an out-of-order delivery move state backwards?
- Does any retry wrap a side effect that is not idempotent?
- For preview-then-confirm flows: is the confirmation bound to the previewed set?
